# Windows运行中的CPU调度补记

本补记不改变模型、插补规则或ZIP中的方法证据；完整收入家族仍在执行。

主机16个逻辑核心的实际采样显示，编号8—15曾全部满载，而0—7负载很低。已经核实PID、创建时间和协调器父链的收入MI worker原先允许使用全部核心，但74.47秒窗口中仅获得约0.276个核心的CPU时间；这不能仅用“16GB内存不够”解释。

对本任务worker作可逆调整：普通优先级提升至above-normal（不是high/realtime），再把亲和性限定为采样时较空闲的0—7核心。之后114.84秒窗口中实际取得0.998个核心的CPU时间，RSS约555MiB、主机可用内存约1.31GiB。统计规格、种子与完整家族门槛不变，仍只运行一个计算worker，没有改动其他任务进程。

这是先后两个窗口的运行观测，不是相同数据的随机性能实验，不能直接称为整批模型提速3.6倍。也没有仅凭编号断言处理器的大核/小核拓扑。后续条件拟合曾记录约6秒，但输入和运行环境同时变化，不能将所有差异归于单一调整。

本任务协调器随后采用相同掩码，以便后续子进程使用；仍须核实每个新worker的实际亲和性。若核心负载分布变化，应恢复原掩码或重新选择，而不是把0—7写成所有Windows机器的固定优化规则。进程结束后该设置不保留为系统级配置。

原始聚合观测见[CPU_SCHEDULING_EVIDENCE.json](CPU_SCHEDULING_EVIDENCE.json)。这项经验已加入[mplusautomation-guide PR #25](https://github.com/lzhs1995/clauder-rstudio-workbench/pull/25)。不涉及新增参与者数据或统计结论。
